# How to Track Versions of Design Files Without “Final Final”

Version confusion usually has two causes: people overwrite earlier work, and approval happens in a chat message that is not connected to the file. A useful version system preserves what changed and makes the approved file unambiguous. It does not require a large project-management system.

## Decide what counts as a new version

Create a new version when a change could affect what someone publishes or delivers: revised copy, altered layout, a new crop, corrected pricing, or a different export setting. Minor internal experiments can stay in the editable source until they are shared for review. The point is to record decisions, not every click.

For the fictional Harborfield Coffee campaign, `v01` is the first shared social graphic. `v02` changes the headline. `v03` corrects the contrast and becomes the approved export. The file names and review note use the same version number. Avoid using `v03` for a later edit merely because it feels small; a recipient who already downloaded `v03` would have no way to tell the files apart.

## Keep work and delivery separate

Use a working area for source files and drafts, a review area for feedback exports, and a delivery area for approved files. A recipient should not need to infer approval from the latest modification time. The newest file may be an unreviewed change.

Do not delete older versions immediately after approval. They may explain a decision or allow a correction to be reversed. Set a retention practice that fits your storage and privacy needs, then apply it consistently. Private customer material needs more careful retention than a public sample graphic.

## Record approval next to the files

A small text note is enough:

```text
Asset: Harborfield Coffee square launch graphic
Current approved version: v03
Approved for: website and social post
Change from v02: headline contrast adjusted
Source: 02-source/harborfield_social-launch_square_source_v03.svg
Export: 04-delivery/harborfield_social-launch_square_final_v03.png
```

For real work, record who approved the file and when, if that matters to the team. Do not claim approval on a public website unless it actually happened. The example above is a teaching sample.

## Handle a change after delivery

Suppose a product name changes after `v03` has been delivered. Make `v04`, note the change, export it, and tell recipients that it replaces `v03`. If the old file was already published, identify where it appears before assuming the replacement is complete. A new file in a folder does not update a website, scheduled email, or social post automatically.

Before delivery, compare the approved source and the exported file. Check that the copy, size, color, and crop match the review decision. Version discipline prevents mix-ups only when the exported result is inspected.
